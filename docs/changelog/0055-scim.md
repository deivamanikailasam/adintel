# 0055 — When someone joins or leaves the company, AdIntel knows

**In one sentence:** the company's identity system can now create, change and switch off AdIntel users
automatically, and switching someone off takes effect immediately.

## What changed

- `api/routers/scim.py` — SCIM 2.0 `/scim/v2/Users` (list with `userName`/`externalId` filters, get,
  create, replace, patch, delete = deactivate) and `/ServiceProviderConfig`; per-tenant bearer tokens stored
  as SHA-256 (`adintel scim token`); SCIM error format; every change audited.
- Governance: provisioned users start with **no approval authority**; approval limits and brand scope can't
  be changed through SCIM (400 `mutability`); delete deactivates rather than erases.
- `security/auth.py` — every request re-checks the stored user: inactive users are refused and token roles
  are intersected with current roles, for dev tokens as well as OIDC (previously a dev token stayed valid
  with its old roles until expiry). Dev login refuses inactive users.
- Docs: `docs/04-security/user-provisioning.md`, security overview, readiness matrix.
- Tests: `tests/api/test_scim.py` (auth and tenant scoping, joiner/mover/leaver, refusal to raise limits,
  token stops working after deactivation, audit trail, invalid roles/filters).

## Why it matters (layman's terms)

The most common way former staff keep access is that nobody remembered to remove them. Now HR's system
tells AdIntel directly, the door locks on the person's next click, and HR's system still can't hand anyone
the authority to spend a client's money — only an AdIntel admin can.
