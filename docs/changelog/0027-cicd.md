# 0027 — CI/CD pipelines and the load test

**In one sentence:** every change is now checked automatically before it can merge, and releasing to
production goes through staging gates and a named human's approval, with automatic rollback.

## What changed

- `.github/workflows/ci.yml` — on every pull request: ruff + format check + mypy --strict; all tests with
  the **85% coverage gate**; integration tests against real Mongo Atlas Local + Redis service containers;
  the **agent evals and the promotion gate** (hard thresholds, category regressions, cost within ±15%);
  bandit, pip-audit, npm audit and a Trivy image scan; Angular build + tests; Terraform fmt/validate.
- `.github/workflows/release.yml` — on merge to main: SHA-tagged image to ECR (no `:latest`) → staging via
  Terraform → E2E golden runs + full evals on staging models (gate) → k6 Monday-peak load test (gate on
  p95) → smoke; then a **manual approval** (GitHub environment = the named sign-off) → blue/green to
  production. AWS access via OIDC, no long-lived keys.
- `tests/load/monday_peak.js` — 50 concurrent runs + 30 chat sessions for 10 minutes; thresholds on error
  rate, API p95 and chat first-token p95 (< 2.5 s); prints the notional AI cost of the busy morning.
- `docs/14-production/environments-and-cicd.md` — environments and the independent lifecycles of code,
  prompts, models, adapters, infrastructure and brand rules, each with its gate and rollback.

## Why it matters (layman's terms)

Prompts, models and code can each break the system in different ways, so each has its own gate — and
each can be rolled back in minutes without touching the others.
